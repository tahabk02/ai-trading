# Environment-variable audit — core-backend, client-app, ai-engine

Date: 2026-10-13 (Morocco Standard Time)
Scope: runtime loading, auto-reload/hot-reload behavior, hardcoded fallbacks, and
fail-closed hardening for the three first-class services. `execution-engine` and
`pocket-bridge` are noted only where they share the pattern.

Method: source inspection of the loaders and every `process.env` / `os.getenv`
site, plus the compose wiring. No values are printed — key names only.

---

## 1. Loading mechanism & reload behavior

| Service | Loader | Files (precedence: high→low) | Resolved from | Hot reload? |
| --- | --- | --- | --- | --- |
| core-backend | `dotenv` | real env → `.env.local` → `.env.<NODE_ENV>` → `.env` | module (`__dirname`), **never cwd** | **Restart required** |
| client-app | Next.js (build) + `server.js` (runtime) | `.env.local` → `.env.<NODE_ENV>` → `.env` (Next) | `client-app/` (Next) | **Rebuild** for `NEXT_PUBLIC_*`; **restart** for server vars |
| ai-engine | `pydantic-settings` | real env → `.env.local` → `.env.<ENVIRONMENT>` → `.env` | module (`Path(__file__).parents[2]`) | **Restart required** |

### core-backend
- `src/config/env.ts:141` `loadServiceEnv()` is idempotent (`loaded` flag, `:85`)
  and is called once at import of `src/config/secrets.ts:21`, before any other
  module reads `process.env`.
- Precedence is implemented by loading highest-first with
  `dotenv.config({ override: false })` (`env.ts:159`): a real injected variable
  (or a higher-priority file) wins; a lower file can never clobber it.
- The parent `<repo>/.env` is **never read**; its existence only triggers an
  advisory warning (`env.ts:97-124`). `CORE_BACKEND_SKIP_ENV_FILES=true` ignores
  all files (`env.ts:145`).
- Values are read **once at boot** → editing `.env` requires a restart.
  `npm run dev` is `ts-node-dev --respawn --transpile-only src/index.ts`, which
  watches `.ts` files, **not** `.env`, so an env edit needs a manual restart.

### client-app — two distinct classes
1. **`NEXT_PUBLIC_*` (browser)**: inlined at **build** time.
   `next.config.js:16-21` puts them in `env`, and browser code must read the
   static literals (`src/lib/env.ts:7-10`, `src/utils/getBaseUrl.ts:71-82`).
   Changing them requires a **rebuild** — a restart is not enough.
2. **Server-side runtime vars**: `client-app/server.js` reads
   `API_PROXY_URL` / `AI_PROXY_URL` / `PROXY_*` / `PORT` / `HOST` at process
   start, and `resolveUpstreams()` (`server.js:177-186`) re-resolves the two
   proxy targets **on every request**. So the upstream targets take effect on a
   process restart (compose recreate) — **no rebuild** needed.
   `next.config.js` `rewrites()` is evaluated **once during `next build`** and
   frozen into `.next/routes-manifest.json`; in production `rewrites()` returns
   `[]` (`next.config.js:63-66`) and `server.js` is the authoritative router.
   The Docker image deliberately bakes **no** proxy env (`Dockerfile:10-12`) so
   one image serves every target.
- There is **no `dotenv`** here; Next loads `.env*` itself, keyed on `NODE_ENV`.

### ai-engine
- `app/core/config.py:63` `Settings(BaseSettings)`, singleton `settings`
  instantiated at import (`:166`). `env_file` = `AI_ENGINE_ROOT_ENV` (`:45`,
  `:154`) — an absolute tuple resolved from the module, highest priority first.
  `case_sensitive=True`, `extra="ignore"` (`:155-156`).
- The parent `<repo>/.env` is **never read** (`config.py:47-53`).
- Read **once at import** → restart required. Dev runs
  `uvicorn app.main:app --reload`, which watches `.py` only; prod CMD is plain
  `uvicorn` (no reload).
- A handful of values are read lazily with `os.getenv(...)` at module import or
  call time (see §3), but the process environment is fixed at start, so they
  are still restart-bound.

## 4. Fail-closed status, and where it leaks

**core-backend — good.** `assertRequiredConfig()` (`secrets.ts:79-123`, invoked
`:127`) collects **all** problems and throws in `production` **and** `test`
(`:121`) for `DATABASE_URL`, `JWT_SECRET` (not placeholder, ≥32 chars),
`AI_ENGINE_API_KEY`. Placeholder detection is real (`env.ts:170` `PLACEHOLDER`);
`file:` is explicitly *not* "configured" (`env.ts:177`). Note the guard is keyed
on `NODE_ENV === "production"` (`:55`), so a deploy with `NODE_ENV` unset gets
the **development** posture.

**ai-engine — leaks.** There is **no boot-time assertion** (unlike core-backend).
`app/api/deps.py:33-34` returns the caller-supplied key **unvalidated** whenever
`settings.ENVIRONMENT != "production"`; the 503 fail-closed path exists only
under `ENVIRONMENT == "production"` (`:36-40`). If `ENVIRONMENT` is unset or
misspelled, the engine accepts **any** `X-API-Key`. Compounding this:
`docker-compose.yml:63` (the *dev* stack) sets `ENVIRONMENT: production` for
ai-engine **without** providing `AI_ENGINE_API_KEY`, so the auth path there
answers 503 for every service call.

**client-app — acceptable.** No secret surface. Unset proxy targets yield a
per-request `503 upstream_not_configured` (`server.js:499-508`) and a self-target
is refused with 500 (`:509-517`) rather than silently looping to localhost.

## 5. Recommendations (fail-closed hardening before production)

1. **ai-engine boot assertion.** Add a `assertRequiredConfig()`-equivalent run at
   settings load: require `AI_ENGINE_API_KEY` (non-placeholder) and a known
   `ENVIRONMENT`; raise at import so a misconfigured engine **crashes at boot**
   instead of silently accepting traffic. Mirror core-backend's collect-all
   error style.
2. **ai-engine auth gate on an explicit flag.** Do not branch on the free-text
   `ENVIRONMENT`; use a dedicated `REQUIRE_SERVICE_AUTH` (default **true**) so a
   missing/typo'd label can never open the engine. Keep the dev escape explicit.
3. **core-backend posture.** Make the required-config guard depend on an explicit
   deployment flag, not `NODE_ENV` alone (an unset `NODE_ENV` currently yields
   the dev posture). Assert `CORS_ORIGIN` non-`*`/non-empty in production, and
   forbid `file:` `DATABASE_URL` outside development explicitly.
4. **Fix the dev compose trap.** `docker-compose.yml:93`
   `${JWT_SECRET:-ultra-secure-secret-key}` is a silent weak default and, with no
   `NODE_ENV: production` on that service, the fail-fast guard never trips.
   Replace with `${JWT_SECRET:?…}`, add `NODE_ENV`, and stop declaring ai-engine
   `ENVIRONMENT: production` in the dev stack (or provide `AI_ENGINE_API_KEY`).
   Align dev vs `docker-compose.prod.yml` (which already uses `:?` guards at
   `:177,:242,:252,:259`).
5. **Fix doc drift.** Root `.env.example:8-11` claims "all services read from
   this single root `.env`" — the code deliberately isolates each service and
   **never** reads the root file (`env.ts:39-42`, `config.py:21-25`). This is
   the exact footgun `env.ts` was written to remove; correct the doc.
6. **Make the contract explicit.** Add one env-contract doc/test enumerating
   required vs optional keys per service (core-backend already implies this via
   `assertRequiredConfig`), and a boot smoke test per service. This closes the
   clean-checkout gap (see `docs/verification/STATUS-NOTE-2026-10-13.md`, PART 47
   [516]) where 4 suites cannot run without a local `.env`.

### Note on reload expectations
Because every service reads its configuration **once at startup**, "change a
`.env` value and have it hot-apply" is **not supported** anywhere. The only
partial exception is client-app's server-side proxy targets, which are
re-resolved per request from an already-started process environment — still a
restart to change, but no rebuild. `NEXT_PUBLIC_*` changes additionally require a
**rebuild**.
